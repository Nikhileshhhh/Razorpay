# ADR 0002 — Gate B4 verification, reconciliation, claims, audit, and demo decisions

- **Status:** Accepted
- **Date:** 2026-08-30
- **Gate:** B4 (verification & demo) — backend PRD §13, §16, §14.1/§14.2 remaining, §15
- **Controlling documents:** `docs/MONEYTRACE_BACKEND_PRD.md`, `docs/MONEYTRACE_ARCHITECTURE_HANDOFF.md` (§7.3, §7.4, §9, §13), `docs/CODEX_REVIEW_CHECKLIST.md`, `docs/GATE_B4_IMPLEMENTATION_PLAN.md`
- **Deciders:** MoneyTrace Buildathon team (executing `docs/GATE_B4_IMPLEMENTATION_PLAN.md` §4)

## Context

Gate B4 adds outcome verification, unique reconciliation, ERP receivable closure, agent-claim retained value and reversal, audit read/export, the frontend-readiness read models, and the deterministic 500-record dataset with demo reset/advance. Several existing B1 schema choices (append-only triggers combined with `is_current` partial-unique indexes, an unnamed reconciliation uniqueness constraint, a mutable `closed_receivable_id` on an append-only table) conflict with the append-only/immutable guarantees B4 requires, and one product shorthand (a claim going straight to `REVERSED`) conflicts with the agent-claim state machine. These decisions resolve those conflicts without weakening any controlling rule; where a rule and a shorthand disagree, the stricter controlling rule wins.

## Decisions

### D1 — Claim reversal follows the existing state machine (no `PENDING -> REVERSED`)

The agent-claim guard (`assertAgentClaimTransition`, architecture §9.2) permits `REVERSED` only from `VERIFIED`/`PARTIALLY_VERIFIED`. The product shorthand "₹1,20,000 − ₹1,20,000 = ₹0 → REVERSED" is realized as a two-step append-only progression:

```
PENDING
-> VERIFIED   (retained 12000000 minor, before the authoritative full refund)
-> REVERSED   (retained 0 minor, after the full refund)
```

Both evaluations are append-only history rows with a moved current head. **Rejected:** adding a `PENDING -> REVERSED` edge (weakens architecture §9.2).

### D2 — Evaluation history is append-only rows plus an explicit mutable current-head table

`claim_evaluations` (and `verification_runs`) carry both an append-only trigger and an `is_current` partial-unique index — mutually exclusive, because marking a new row current requires updating the prior row, which the trigger forbids. Resolution: keep history tables strictly append-only; add explicit mutable head tables `claim_evaluation_heads` and `verification_run_heads` that point at the current version. History is never mutated; only the head row moves. Migration `0004` backfills heads by highest version and removes the contradictory partial-current indexes / deprecated `is_current` columns. **Rejected:** updating an old evaluation's `is_current` (violates append-only).

### D3 — Allocation, closure, and reversal are separate append-only facts

Never update `reconciliation_allocations.closed_receivable_id` or `status` (the table is append-only). Add append-only `receivable_closures` and `reconciliation_reversals`. Read models derive current logical state by joining allocation + closure + reversal facts, so historical reconciliation survives a later reversal intact. **Rejected:** mutating the allocation row to record closure/reversal.

### D4 — Reconciliation proves candidate-set cardinality (never `LIMIT 1`)

An allocation is legal only when, after exact tenant/currency/recipient/amount/UTR/value-date-window predicates and row locks, the complete eligible set contains exactly one expectation and exactly one unconsumed authoritative bank line. Races are classified deterministically: identical allocation identity → idempotent existing allocation; a different expectation or bank-line contender → `RECONCILIATION_AMBIGUOUS` with an appended unresolved audit fact and no second effect; raw PostgreSQL constraint text never escapes the service or logs. **Rejected:** amount-only/name-fuzzy/first-row/ingestion-order/random-id tie-breaking.

### D5 — Receivable closure is a registered automatic action with layered authorization

Add plan template `CLOSE_RECEIVABLE_AFTER_RECONCILIATION` bound only to tool `CLOSE_SYNTHETIC_RECEIVABLE_AFTER_RECONCILIATION`, with authority level `L3`, zero money impact, and a typed `expectation_id` parameter. Closure proceeds only when every layer agrees: (1) a registered typed plan exists; (2) deterministic policy receives a persisted reconciliation projection and returns `ALLOW_AUTOMATIC` for a branded trusted worker actor; (3) reservation re-locks and revalidates the exact allocation, the authoritative bank evidence, the absence of a reconciliation reversal, and the absence of an existing closure; (4) the worker-only ERP adapter accepts only the reconciled expectation and close action; (5) adapter ACK records only a request — a signed `SellerReceivableClosed` event correlated (`causation_id`) to the close action is required for observed closure. The generic public `evaluate-policy` endpoint cannot manufacture the reconciliation projection, so it continues to deny CLOSE. The policy input carries a typed `reconciliation_state` object (allocation/expectation/status/closure/reversal/version or explicit `null`), **not** a lone authorization boolean.

### D6 — Cross-module orchestration joins one caller-owned transaction

Reconciliation/reversal flows must not call public wrappers that each open independent transactions. Add narrowly scoped transaction-aware variants while preserving the public wrappers: `openOrGetCaseInTransaction`, `evaluateCasePolicyInTransaction` (server-resolved user actor or branded worker actor), `reserveActionInTransaction` (same actor distinction + CLOSE hard gate), plus verification/outcome/head helpers required by the caller transaction. Continue reusing the already-present `proposePlanInTransaction`, `lockControlLoopCase`, and `transitionCaseInTransaction`. No B4 module writes another module's tables directly when a public application service owns that state.

### D7 — Verification predicates and financial metrics are contract-specific

"Observed ERP closure" is **not** a universal predicate. Transfer remediation (`TRANSFER_REMEDIATION_VERIFICATION`) requires transfer, recipient settlement, independent bank evidence, unique allocation, and observed ERP closure; its verified amount is `45500000` for the main scenario. Receivable closure (`RECEIVABLE_CLOSURE_VERIFICATION`) requires the correlated ERP closure observation after a still-valid allocation; its verified amount is `0` (a state effect, not additional restored money). Recovery suppression (`SUPPRESS_RECOVERY_VERIFICATION`) requires observed signed recovery-suppression evidence; its amount feeds only the prevented-loss metric. `REQUEST_MORE_EVIDENCE` has a no-effect contract and no adapter dispatch. `verified_restored` sums only current verified transfer-remediation outcomes, grouped once per expectation, and never double-counts the CLOSE run.

### D8 — Unknown action outcomes remain observable, not retryable

Both `ACKNOWLEDGED` and `OUTCOME_UNKNOWN` may create a pending verification run and a status-check job. `OUTCOME_UNKNOWN` stays explicitly unknown until independent authoritative evidence proves/disproves the effect or the contract times out. No new idempotency key or blind adapter retry is allowed.

### D9 — "500 records" is an auditable imported dataset ledger, not 500 subjects

The backend PRD's "exactly 500 accepted synthetic lifecycle records" is realized as an append-only `demo_dataset_records` ledger linking exactly 500 imported source records to their accepted, non-quarantined `ingest_events` rows. A subject may own several records; record count and subject count remain distinct diagnostics. Live scenario-step evidence is operational evidence, not a dataset item. The manifest counts the 500 ledger items, verifies each has exactly one accepted non-quarantined journal row, and computes every metric from persisted rows (never narrative constants). Hidden expected labels stay under `fixtures/hidden-ground-truth`, importable only by tests; runtime dataset rows carry stable identifiers and provenance, never ground-truth labels.

## Consequences

- Migration `0004_b4_integrity.sql` is forward-only and idempotent, never rewriting `0001`–`0003`; it renames the reconciliation constraints to stable runtime names, adds the append-only closure/reversal/head/dataset tables, adds `agent_result_claims.request_hash`, and adds composite tenant FKs and indexes.
- Read models and manifests are derived from persisted rows; narrative constants appear only as test expectations.
- The pure money kernel and independent state machines are reused unchanged; no new infrastructure or external dependency is introduced.
