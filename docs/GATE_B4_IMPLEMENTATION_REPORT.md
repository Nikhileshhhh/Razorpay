**Honest transaction-boundary note (plan §5.1's "do not claim false atomicity"):** the truncate+identity/policy/source/verification-contract seed is one atomic transaction. The subsequent 500-record generation is **not** nested inside that same transaction — several buckets invoke public application services (`runInvestigation`, `evaluateCasePolicy`, `reserveAction`, `dispatchAction`, `evaluateActionVerification`) that each open and commit their own transaction, and node-postgres/Drizzle transactions cannot safely nest across independently-transactional service calls at this scope. `generateDemoDataset` therefore runs as an **ordered sequence of independently atomic steps**; a failure partway through leaves a partially seeded _disposable_ demo database, which the next reset's leading `TRUNCATE` always repairs from a clean slate. This is documented in code comments in `dataset.ts` and `reset.ts`, not silently claimed as one all-or-nothing transaction.

**Measured runtime cost:** a full reset (500 real records + the one CTRL-04 flow) takes **~62–70 seconds** measured repeatedly. `vitest.config.ts`'s `hookTimeout` was raised from 60s to 180s specifically to accommodate this in the handful of test files that call `resetDemoDatabase` (`identity-and-reset.test.ts`, `b4-scenarios.test.ts`, `b4-reconciliation.test.ts`, `dataset-flows.test.ts`, `b4-manifest.test.ts`) — no B1–B3 test file was touched for this, since none of them call `resetDemoDatabase`.

## 5. Real defects found and fixed this session

1. **Concurrent-query correctness bug** in `src/modules/actions/action-service.ts` (CLOSE reservation hard gate): three locked reads (`receivable_closures`, `reconciliation_reversals`, `ingest_events`) ran concurrently via `Promise.all` on the single pinned transaction connection. node-postgres cannot execute concurrent queries on one connection (emits a deprecation warning, removed entirely in pg@9, and risks response interleaving). **Fixed**: rewritten as sequential awaits. Verified: the deprecation warning disappeared from scenario test output and all scenario/reconciliation tests still pass.
2. **`SUPPRESS_SIMULATED_RECOVERY` verification never reported an amount** in `src/modules/verification/verification-service.ts`: `verifiedAmountMinor` was hard-coded to `null` for every tool except `CLOSE_SYNTHETIC_RECEIVABLE_AFTER_RECONCILIATION` and `SIMULATE_TRANSFER_REMEDIATION`, even when the contract reached `EFFECT_VERIFIED`. This directly blocked `duplicate_collection_prevented` from ever being measurable. **Fixed**: the suppressed-recovery evidence's own amount is now captured and returned when the contract verifies. Verified via `dataset-flows.test.ts`'s CTRL-04 test and the full manifest test.
3. **Reconciliation-metrics scoping bug** (found while building the manifest metrics, not a pre-existing regression): the first draft of `unresolved_cases`/`unsafe_candidate_matches_blocked` counted every active CTRL-01 case tenant-wide, which double-counted a named scenario's own missing-transfer case (e.g. `claim-reversal`'s capture-with-no-transfer legitimately opens its own CTRL-01 case). **Fixed**: scoped to cases whose subject appears in the `demo_dataset_records` ledger, per ADR 0002 D9 ("live scenario-step evidence is not a dataset item"). Verified: `unresolved_cases` stays exactly `16` after both `claim-reversal` and `missing-transfer-remediation` fully advance.
4. **`data_imports` append-only violation**: the first draft of `generateDemoDataset` tried to `UPDATE` the `data_imports` row (to set `accepted_count`/`manifest_hash` once known) — `data_imports` has a real `forbid_update_delete` trigger (migration `0004`), so this failed outright. **Fixed**: every column is now computed and supplied at the single insert, before any ledger row exists; the manifest hash (which needs all ledger rows to exist first) lives on `demo_seed_manifest` instead, and `getImportResult` was updated to read the hash from there rather than asserting a non-null `data_imports.manifest_hash`.
5. **`SellerReceivableClosed` worker-poisoning risk** (backend PRD §18/continuation review item, not something break the tests but a real robustness gap): `src/worker/job-handlers.ts`'s `project-evidence.v1` handler called `observeReceivableClosure` with no guard, so an unrelated/invalid closure event (wrong action/expectation/tenant, missing causation, already-reversed allocation) would throw `ReceivableClosureInvalidError` as an uncaught, retryable job failure. **Fixed**: the error is now caught and safely ignored (matching the existing pattern immediately below it for refund/reversal events), never treated as a job failure.
6. **Reconciliation retry silently under-reported closure state**: a repeated `reconcileExpectation` call after the receivable was already observed-closed always returned `closed_receivable_id: null`, contradicting the persisted fact. **Fixed**: the real `receivable_closures` row (if any) is now looked up and reported on every call, matching the `ReconciliationResult` contract's own `closed_receivable_id: OpaqueId.nullable()` design for the `ALLOCATED` status. Verified with a new assertion in `b4-reconciliation.test.ts`.

None of these required weakening any test, schema, or safety rule; all were root-caused and fixed at the source.

## 9. Known limitations and explicitly deferred scope

These are honest gaps, not silently omitted:

1. **Data Health fields left at measured-`0`, not fabricated**: `schema_failure_total`/`unlinked`/`stale_projections`/`projector_lag_seconds`/`job_lag_seconds` are not backed by any existing persisted tracking (a schema-rejected payload never reaches the journal at all; lag would require persisting enqueue-vs-completion deltas the current `projector_runs`/`outbox` schemas do not yet expose). Documented inline in `demo-service.ts` and here rather than presented as "no failures ever occurred."
2. **Worker/job-handler tenant environment is hard-coded to `'demo'`** in `createTenantContext(payload.tenant_id, 'demo')` across `job-handlers.ts`, `job-handlers-b3.ts`, `job-handlers-b4.ts`, and `source-auth.ts`. This is a **pre-existing, systemic pattern established in B2/B3**, not introduced or worsened by B4 — fixing it correctly would mean looking up each tenant's real `environment` column consistently across all of these files at once (a cross-gate change), which is out of this session's B4-only scope. ### 11.1 P0 defect → fix → verification

1. **Agent-claim evaluation was not bound to non-empty validated evidence, and retained-value inputs were incomplete.**

   - **Fix:** [`src/contracts/agent-claims.ts`](src/contracts/agent-claims.ts) — `evidence_refs` now `.min(1)`. [`src/modules/claims/claim-service.ts`](src/modules/claims/claim-service.ts) — `linkedReversals` is now summed from `SyntheticTransferFailed` evidence for the claim's subject; `independentlySatisfiedBaseline` is now the sum of MoneyTrace's own `EFFECT_VERIFIED` `SIMULATE_TRANSFER_REMEDIATION` outcomes for expectations belonging to the same economic subject (joined through `verification_run_heads` → `verification_runs` → `actions` → `cases` → `economic_subjects`); `linkedDisputes` stays honestly `0` with an inline comment — no canonical dispute event type exists in the closed vocabulary (architecture §8.2), so this is a documented, structural limitation, not a silently dropped input.

2. **Reconciliation candidate enumeration was not genuinely tenant-wide, and a self-introduced gap was found and fixed mid-remediation.**
   - **Defect (original):** the pre-existing implementation found candidates by asking "does my own subject's evidence contain a unique match", which could never detect a bank line also exactly matching a _different_ expectation's evidence, and serialized reconciliation per-expectation (not tenant-wide), leaving a race between two expectations contesting the same bank line.
   - **First fix (this session) — later found incomplete:** `tenantWideCandidates` was rewritten to lock every current expectation and all eligible bank/settlement evidence tenant-wide under a single tenant-wide advisory lock, with a typed `ReconciliationAmbiguousError`/`reason` (`multiple_candidates` | `contested_bank_line`). While implementing the adversarial tests this fix was supposed to enable, it became clear the candidate search still bucketed **both** settlement and bank evidence by the bank row's own `economic_subject_hint` — an ingestion-time guess, not ground truth. Since PostgreSQL enforces at most one current expectation per subject (`expectations_current_uq`), a bank row's hint bucket could structurally only ever backed one expectation's candidate set, meaning `contested_bank_line` could **never actually trigger** — a real gap, not a hypothetical one.
   - **Root-caused fix:** `exactCandidates` (`src/modules/reconciliation/reconciliation-service.ts`) now pairs each expectation's own subject-scoped settlement evidence against the **complete tenant-wide pool of bank evidence** (not filtered by the bank row's own hint), so the same physical bank evidence row is checkable against every current expectation's settlement, genuinely enabling detection of one bank line satisfying two different expectations.
   - **Verified:** `tests/integration/db/b4-reconciliation.test.ts` — two new tests added and passing against real PostgreSQL: _"one bank line contested by TWO DIFFERENT expectations abstains for both"_ (proves the fixed gap is now closed) and _"one expectation matching TWO independent bank credits is ambiguous"_ (the symmetric case). A third new test, _"two genuinely independent expectations reconciled in PARALLEL both allocate correctly"_, drives two concurrent `reconcileExpectation` calls via `Promise.all` and proves the tenant-wide advisory lock serializes them into two correct, non-cross-contaminated allocations. A fourth new test proves the 2-day value-date tolerance boundary (`<=` inclusive) is exact, not approximate.

4. **Imports were not genuinely asynchronous or retry-repairable.**
