1MoneyTrace — Verification Timeline · eleven stages, six states (desktop only, as requested)

Making the evidence threshold legible

ELEVEN STAGES, NEVER COLLAPSED

Submission, acknowledgement, transfer, recipient settlement, bank proof, allocation, closure requested, closure observed and terminal outcome are nine separate rows — never one progress bar. The connecting rail stops at the last completed fact and is grey beyond it.

SIX DISTINCT STATES

Waiting (hollow circle), Complete (filled check), Blocked (triangle), Failed (filled cross), Unknown (question glyph) and Reversed (reverse arrow) each carry shape + icon + text + tint. Unknown is never styled as Failed; Failed is reserved for a genuinely failed stage.

THREE-PART THRESHOLD

"Verification requires authoritative evidence, unique reconciliation, and observed closure" sits in every header. Stage 11 can only read VERIFIED when stages 7, 8 and 10 are each explicitly complete — the rule is printed next to the three stages it governs.

READ AND CHECK

Reads bind to GET /v1/cases/:id/verification. Check status posts to /v1/actions/:id/verification-checks at the persisted run version. OUTCOME_UNKNOWN never offers Retry, Resubmit or Execute again.

TIMELINE ANNOTATIONS
Two statuses, never merged

The header carries ACTION STATUS and FINANCIAL OUTCOME side by side with different glyph families. Whenever action status is ACKNOWLEDGED or OUTCOME_UNKNOWN it also gets its own banner below the header, so the two can never be read as one result.

The rail stops at the last fact

Green 2px rail through stages 1–3; from stage 4 onward it is neutral #dfe3ea. Nothing ahead of the last completed fact is ever tinted as progress, and there is no percentage, no "4 of 11 done", and no completion animation.

Semantics

A real ol with one li per stage, so screen readers get stages 1–11 in order regardless of layout. Each state glyph is an img with its state as the accessible name; timestamps carry exact UTC in the title; money carries a spoken label.

Required-for-VERIFIED tags

Stages 7, 8 and 10 carry a blue REQUIRED FOR VERIFIED tag in every state variant, so the threshold is visible while it is still unmet rather than only explained after the fact.

Stage 3 · FAILED (reserved usage)

Failed appears only when a stage genuinely failed — here, submission was rejected by Synthetic Route with a determinate error at 25 Aug 11:03 IST. Missing evidence is Blocked; an indeterminate response is Unknown. Neither is ever styled as Failed.

Verification timeout is a blocker, not a failure: the contract stopped waiting for a source read. Blockers vocabulary in use — Missing bank credit, Identity mismatch, Currency mismatch, Time-window mismatch, Multiple candidates, Closure not observed, Verification timeout.

MONEY FORMATTING — BINDING ANNOTATION

Verification amounts remain decimal-string minor units and are formatted with BigInt only — never Number() or parseFloat(). Verified, reversed and retained amounts are three separate server fields; the browser never subtracts one from another.

verified_minor: "45500000"
reversed_minor: "-12000000"

Read and check

GET /v1/cases/:id/verification drives the whole panel. Check status posts to /v1/actions/:id/verification-checks with the persisted run version, shows an in-flight state, then refetches the authoritative result — no locally derived stage state, ever.

Announcements without chatter

One polite announcement per genuine state transition — "Bank evidence matched. Verification still incomplete: 2 blockers." Repeated identical poll results announce nothing. Reduced motion removes all transitions; state changes are instant, and no completion animation exists in any state.

Never in this panel

No "AI verified", no generic "Success", no percentage complete, no celebratory animation, no Retry or Resubmit on Unknown, no automatic resolution of ambiguity, and no single collapsed progress step.
