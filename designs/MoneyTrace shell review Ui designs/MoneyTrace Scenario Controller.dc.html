A queued request can never look like a completed financial result

TWO NUMBERS, ALWAYS BOTH

Every card prints completed_step and current_step as separate facts — "Completed 2 of 6 · Step 3 queued". There is no percentage, no bar that fills on request, and no state where a queued step is drawn as done.

200 IS NOT COMPLETION

Advance queues work; the drawer then polls GET /v1/demo/status and only persisted completed_step moves the UI. Status is never derived from a mutation response.

EVERY COMMAND STATES ITS BASIS

Expected step and persisted state_version travel with the request and are visible in a read-only Command basis disclosure. A stale version invalidates the action rather than overwriting newer state.

SYNTHETIC, AND SAID SO

Reset rebuilds 500 deterministic synthetic records. The dialog states plainly that no real Razorpay or bank data is involved, and the destructive styling is deliberately restrained so it can't read as real-account deletion.

CONTROLLER ANNOTATIONS
Focus behaviour

Initial focus lands on the drawer heading (tabindex="-1", shown focused here), focus is trapped while open, Escape closes, and focus returns to the "Demo scenarios" header trigger — which keeps its own focus ring behind the scrim so the return target is obvious.

Progress is text first

"Completed 3 of 6 · Step 4 queued" is the accessible truth; the segment strip is aria-hidden decoration where the queued segment is drawn as an outline, never a fill. No scenario ever shows a percentage.

Advance is disabled when it would be unsafe

Disabled while a request is in flight and whenever current_step > completed_step — i.e. work is already queued. Next allowed step is a single value, so an operator can never skip ahead. See 1b.

Role boundary

The header trigger is absent for Viewer, Investigator and Finance Approver — not disabled — so no dead control implies latent power. Other roles still see the current scenario stage as read-only context in Overview. Backend 403 on every mutation endpoint remains the authoritative boundary; hiding the trigger is convenience only.

Not an animation tool

No timeline scrubber, no autoplay, no step preview, no simulated pipeline motion. Every control maps to one real persisted backend command, and the drawer's state comes from GET /v1/demo/status alone.

API BOUNDARIES — WHAT EACH CALL MAY AND MAY NOT DO
GET /v1/demo/status

The only source of displayed state: current_step, completed_step, status, state_version, last_error. Polled while queued and while a tab is visible.

POST …/:id/advance

Queues the expected next step with expected step and persisted version. A 2xx means accepted, never completed — the UI advances only after a status read confirms it.

POST /v1/demo/reset

Runs only after typed confirmation, carrying expected seed and version. Completion is read from persisted state, then caches clear and Overview loads.

MONEY FORMATTING — BINDING ANNOTATION

Manifest and scenario money values stay API decimal strings in minor units, formatted with BigInt only — never Number() or parseFloat(). The controller displays each figure as returned and never nets restored against reversed to produce a "current total".

Accessibility contract

role="dialog" aria-modal="true" labelled by the heading, which takes initial focus. Focus trapped; Escape closes; focus restored to the header trigger. Scenario cards are a keyboard radiogroup (arrows move, Space selects). Every status is glyph plus text; exact step, total and version are plain text available to assistive technology, not tooltip-only. The reset dialog has a focusable error summary linking to its field. Live regions are polite and fire once per real transition — queued, completed, failed, stale, reset complete — never per poll. Reduced motion removes the drawer slide; it simply appears.

Non-operator behaviour

For Viewer, Investigator / Case Manager and Finance Approver the header trigger is not rendered at all, so there is no disabled control hinting at hidden power. Current scenario stage remains visible as read-only context elsewhere in the product. If a mutation endpoint is reached anyway — deep link, replay, stale tab — the backend returns 403 and the UI shows the standard "Action refused by server" notice; hiding the trigger is never treated as the security boundary.

Never in this controller

No credentials, connection strings, keys, raw worker/provider/database messages, stack traces or payload dumps. No real-money implication, no percentage progress, no fake pipeline animation, no "In progress" status invented between Queued and Completed, no skip-ahead step picker, and no reset control anywhere outside this dialog.
